## 0. 先把这个项目讲明白

### 30 秒版

> 我做了一个内容推荐的全链路系统，按真实工业架构分了召回、精排、重排和用户增长几层。
> 召回开了三路——ItemCF、双塔向量、时间衰减热榜——用 RRF 融合，Recall@50 从单路最强的 0.21 提到 0.257；
> 精排实现了 DeepFM、DIN 和 ESMM 多目标，DIN 用 target attention 把 AUC 从 0.798 提到 0.819，
> ESMM 额外给出 CTCVR-AUC 0.847；最后加了多样性重排，让列表多样性提升 35% 的同时 NDCG 还涨了 9%。
> 另外单独做了新内容冷启动和用户增长两个模块，冷启动如果不开独立通道 Recall 就是 0，开额度 20 后能到 0.40。

### 3 分钟版（讲完停下来等他问）

在上面基础上补三段：

1. **为什么要做**：JD 里的关键词散着说没意义，我想验证它们串成链路后会怎么互相影响——
   比如召回漏掉的候选，精排再强也救不回来（实测召回命中率 0.257 就是精排的天花板）。
2. **最有价值的发现**：我在 DIN 上踩了一个标签泄漏——训练时目标物品就在用户的行为序列里，
   模型学会"历史里有→点击"，train loss 掉得很漂亮，valid AUC 却从 0.65 崩到 0.60。
   加了因果掩码之后双塔 Recall@50 从 0.145 涨到 0.215，DIN AUC 恢复到 0.819。这条经验比模型结构值钱。
3. **还没做完的**：负样本还没上 hard negative；多模态只做了文本侧；没有在线 AB 闭环。这是下一步。

### 一句话定位

> 不是一个"调包跑个 DIN"的项目，是一套**带评测护栏和失败复盘的可运行系统**。

## 1. STAR 故事（可直接在面试里讲）

### STAR-1：把 ItemCF / 双塔 / 热度三路召回融合起来

- **S（情境）**：单路召回各有硬伤——ItemCF 冷启动无解、双塔在小物空间压缩损失大、热榜没有个性化。
- **T（任务）**：不能丢掉任何一路的互补信息，还要避免不同量纲的分数打架。
- **A（行动）**：
  - ItemCF 加 IUF 加权抑制活跃用户的噪声共现，相似度只保留 Top100 近邻；
  - 双塔用 batch 内负样本 softmax + 流行度 logQ 修正训练，物品塔接内容语义向量；
  - 融合用 RRF（只看 rank，不看原始分），三路权重 0.6/1.0/1.0。
- **R（结果）**：Recall@50 热度 0.112 → ItemCF 0.188 → 双塔 0.207 → **融合 0.257**，比最强单路高 24%。

### STAR-2：DIN 目标泄漏的定位与修复（最有含金量的一段）

- **S**：第一版精排训练时，DIN 的 train loss 从 0.44 一路降到 0.24，看起来非常好。
- **T**：valid AUC 却从 0.65 掉到 0.60，说明model 学到的东西不对劲。
- **A**：
  - 定位：训练样本的行为序列包含**当次目标物品本身**，模型学会"历史里有该 item → 点击"这条捷径；
    而评测时目标物品不在历史里，于是所有正例都被打低分。
  - 修复：为每条样本算 `hist_keep`（该曝光时刻之前保留几条行为），在 batch 构造时把之后的位置 mask 掉；
    负样本必须和对应正样本共享同一个 keep 值，否则模型会从"历史长度"反推标签。
  - 护栏：写了 `test_causal_mask_file_consistency`，校验每个样本块内的 keep 值一致。
- **R**：双塔 valid Recall@50 0.145 → **0.215**；DIN AUC 0.60 → **0.819**；测试 42 条全绿。

> **讲这段的加分话术**："loss 优化得越漂亮，模型可能错得越离谱。所以我对所有看起来太好的训练曲线都会先怀疑一次。"

### STAR-3：新内容冷启动（对 B站"UP 主与内容生态"这条 JD 特别对口）

- **S**：93 件"全新内容"（训练集中行为全部抹除），纯协同模型的 Recall@50 是 **0.0000**。
- **T**：新内容必须获得曝光，但又不能靠牺牲大盘体验硬塞。
- **A**：新增两条独立通道——内容语义（bge 向量 + 用户历史均值画像）与标签倒排；
  设计"扶持额度"旋钮（每ユーザー候选里几个坑位留给新内容），并测量不同额度的召回/覆盖。
- **R**：额度 20 时 Recall@50 **0.401**，新内容曝光覆盖率 **98.9%**；额度是一个可运营的连续旋钮。

### STAR-4：用户增长 Lookalike + pLTV

- **S**：业务要拉新/召回流失用户，只有一小撮已知高价值种子名单。
- **T**：把种子扩成一个够投放规模、还能保证质量的人群包。
- **A**：先用 SVD 用户向量做 KNN 投票扩展，再用 pLTV 价值模型筛掉低价值用户（两步法）。
  为避免先导未来信息，价值标签按时间窗口单独切（后 20% 作为未来），用户向量只用过去窗口算。
- **R**：随机基线 Lift 1.03x → 质心扩展 1.82x → KNN 2.08x → **KNN+pLTV 3.88x**（命中率 77.8%）；
  pLTV 本身 Spearman 0.611、高价值识别 AUC 0.918。

> **加分话术**："相似度解决的是像不像，价值模型解决的是值不值，这是两个问题。"

## 2. 高频追问与标准答案

### A. 召回为什么会漏?怎么诊?

- **先看召回层的天花板**：本项目中召回融合的 Recall@50 = 0.257，意味着 **74% 的正例在进入精排之前就已经丢了**。
  精排 AUC 再高，也只能在这 25.7% 里做排序。
- **诊断顺序**：①候选数够不够 ②各路去重后单一路占比有没有过高（说明融合权重失效）
  ③新内容是否在候选里出现过（冷启动通道有没有生效）④ANN 的 nprobe 是不是设得太低。
- **本案数据**：ItemCF 与双塔的重叠度不高，融合后比单路高 24%，说明多路确实互补；
  如果两路结果高度重合，就应该换 channel 而不是继续堆权重。

### A2. 为什么双塔要用 batch 内负样本？不够难怎么办?

- batch 内负样本（in-batch negatives）把 batch 里其它正样本的 item 当负例，
  一次前向就能得到 B-1 个负例，效率极高，而且这些负例天然来自"别人喜欢的"分布，
  比纯随机负例更有区分度。
- **流行的代价**：热门 item 频繁出现在 batch 里，会被过度惩罚 → 用 **logQ 频率修正**
  （本仓库实现了，tau=0.05）。
- **不够难时**：混合"召回 top-N 但没点击"的样本作为 hard negative，或者用难负例挖掘。
  本项目目前还没做，这是已知的改进点（README §6 明写了）。

### A3. Softmax 损失和 BCE 有什么区别？为什么召回用前者?

- softmax 是 **listwise**，让目标 item 在整批 candidate 中的相对分数最大；
  BCE 是 pointwise，只关心这一对的绝对概率。
- 召回的本质是"从全库挑 top-K"，是排序问题，所以用 softmax 更贴；
  精排预测绝对点击概率（线上要用于计费/混排），所以用 BCE 保证概率校准。

### B. DIN 和双塔/DIEN 的区别?

- 双塔：user/item 各自出向量，**互相之间无交互**（只有最后一次点积），适合 ANN 检索，但表达力受限。
- DIN：候选 item 参与 item sequence 的 attention 计算，兴趣随候选变化。
- DIEN：进一步建模兴趣**演化**（GRU + AUGRU），不只是静态 attention。
  → 诚实地说：本项目只做到 DIN，DIEN 的序列建模（GRU 时序）是下一步。
- **为什么 DIN 只提升 2pt 而不是更多？** 因为本数据集每个用户的历史被截断到 50 条，
  且 MovieLens 的兴趣迁移不如电商/短视频明显；在真实短视频场景，兴趣迁移快，
  DIN/DIEN 的收益通常更大。这个"敢为帀界"的回答比吹嘘收益更可信。

### B2. DeepFM 和 DIN 谁更强，为什么都做?

- DeepFM 是"无序列"的上限：FM 显式二阶 + DNN 隐式高阶。
- DIN 是"有序列"的代表。**同输入、只变结构**的对比才有意义——本仓库三者共享同一份 embedding 底座，
  所以 2.15pt 的差距可以干净地归因给 target attention。

### B3. ESMM 解决什么问题？和 MMOE 有什么区别?

- **问题**：CVR 的标签只在点击样本里有，直接用它们训练会有 SSB（sample selection bias）
  和 DS（data sparsity）两个问题。
- **ESMM 的解**：`pCTCVR = pCTR × pCVR`，在**全曝光空间**上监督 CTCVR，
  同时用点击样本监督 CTR，两个塔共享底层。CVR 是副产品，不需要编造标签。
- **和 MMOE 的区别**：MMOE 用多个 expert + 门控做**任务间的软共享**，缓解负迁移；
  ESMM 解决的是**标签空间不一致**。两者可以叠加（ESMM 的底层换成 MMOE）。
- **本仓库观测到的负迁移**：ESMM 的 CTR-AUC 0.814 略低于纯 DIN 0.819——
  这是多任务的典型代价，用一句话承认它，比假装没发生更专业。
  > 追问："那你还用多目标吗？" → "用，因为我需要 CTCVR。但如果线上只优化点击，我会拆成单任务或者用 PLE 做隔离。"

### C. 负采样为什么用 popularity^0.75?

见 系统设计.md §1。要点：均匀负采样会让模型过度学习长尾（很多负样本其实从未真实曝光），
0.75 次幂是 word2vec 的经验参数，能在"贴近真实曝光分布"和"保留中长尾信号"之间取平衡。

### C2. 正负样本比例 1:4 会不会有问题?

- 1:4 会让训练分布的正负比偏离真实（真实 CTR 通常 1%~10%），
  预测出的 pCTR 是**偏高校准**的（约等于把真实 CTR 放大）。
- 工业做法：训练时用负采样加速，**线上用前做负采样校正**（`p_real = p*(1-r)/(p*(1-r)+r*…)`），
  或者在 loss 里加 importance weight。
- 本仓库没有做校准——因为评估指标是 AUC/GAUC（rank 指标，单调变换不变）。
  如果要上线做混排/计费，必须校准。这是很加分的一条自省。

### D. 为什么要做重排？牺牲精度换多样性值得吗?

- 精排是 pointwise，无法建模"列表内的相互关系"，会导致同一 UP 主/同一系列/同类封面占满一屏。
- 本项目实测：**类目打散反而同时提升 NDCG@10（+9%）和 ILD（+35%）**——
  因为同质占位让位之后，真正相关的长尾才有机会浮上来。
  所以"多样性必然牺牲精度"是个**可以被数据推翻的直觉**。
- MMR 的 λ 是连续旋钮：λ→1 趋向精排，λ→0.5 多样性更强。可以给不同人群/场景配不同 λ。

### E. 冷启动除了内容还有什么办法?

- **物品侧**：内容向量/标签/Bandit 探索（Thompson Sampling、UCB）给新内容保量曝光。
- **用户侧**：人口属性、设备、地域即时画像；首屏用热门+轻量问卷/兴趣选择。
- **机制侧**：流量扶持额度、探索/利用分流、创作者侧保量承诺（对 B站"UP 主生态"尤其重要）。
- **本仓库选择**了"内容通道 + 额度旋钮"，因为它可量化、可运营。

### F. GDPR/隐私、去重/打散、频控、负反馈怎么考虑?

> 这类追问通常出现在 B站/Kwai 这种社区场景。
- 负反馈（不感兴趣）必须做成**实时降权特征**而不是只做过滤；
- 已看/已曝光内容要进入 30 分钟~7 天的频控缓存；
- 打散维度不只用类目，还要用作者/封面/标题相似度；
- 本次项目里我做的是**类目 + 内容余弦相似度**两个维度的 MMR。

### G. 服务端怎么推理？延迟多少?

本项目实测（6038 用户全批量打 80 条候选）：

| 阶段 | 耗时 |
| --- | --- |
| 召回：双塔 + ItemCF + 热度 | ItemCF 93ms（全量，可离线预计算）, 双塔 9ms, 热度 0.8ms |
| 精排打分 | **0.12 ms / 用户**（含 80 条候选，GPU batch） |
| 重排 MMR | 亚毫秒级 |

优化点：ItemCF 相似度应该离线算好后只在线做 top-K 聚合；用户 Embedding 每 5~30 分钟更新一次即可。

### H. 离线指标涨了，线上不一定涨，你怎么看?

- 常见原因：①指标与业务目标不一致（AUC vs 时长/留存）②只有 surge——离线用曝光样本、线上是全量，
  exposure bias ③数据穿越 ④AB 分流不均 / 新奇效应。
- 我的做法是**先怀疑数据再怀疑模型**：这个项目里两次泄漏都是这么抓出来的（train loss 越漂亮越可疑）。
- 如果让我上线第一版，我会同时看交互指标（CTR/时长）和生态指标（覆盖率/作者侧分布），
  并且一定会看 7 日留存而不是只看当天。

### H2. 你怎么做 A/B 实验?

- OEC（overall evaluation criterion）先定死；随机数维度用 user-level hash，且要有 AA 校验证明分流无偏；
- 样本量用最小可检测效应（MDE）估算，不达标不提前开奖；
- 新奇效应：首周数据要标注，最好做 holdback。

### I. SQL 会写到什么程度?

- 本项目画像特征全是 DuckDB SQL：CTE、窗口函数（`ROW_NUMBER`/`COUNT DISTINCT DATE_TRUNC`）、时间衰减窗口函数。
- 常见考点我会：留存/漏斗的 `LEFT JOIN + GROUP BY`、去重计数 `COUNT(DISTINCT)`、
  同比环比 `LAG/LEAD`、以及 Top-N per group 的窗口函数写法。
- 扩展：Hive 的差别在于分区、`GROUPING SETS`、数据倾斜处理（salting / skew join）。

### J. LLM 在推荐里能干什么?（两条 JD 都点名了）

- **内容理解侧**：标签/标题/摘要生成、封面 OCR 后多路校验、多模态 Embedding（本仓库的文本语义塔就是这一步）。
- **召回侧**：语义 ID / 生成式推荐（TIGER 风格）、LLM 做用户意图理解后打分或改写 query。
- **工程侧**：LLM 生成样本/特征解释、给运营做策略分析助手、RT 之外的 explainability。
- **注意边界**：LLM 不适合直接在线推理（延迟/成本），通常产出**离线物料**（标签、向量、候选池）。
  我在项目里就是这么用的：离线生成受控词表标签 + 入库倒排。

### K. 你同时在投游戏社区和视频社区，它们推荐目标有什么不同?

| 维度 | 游戏社区（米哈游） | 视频/直播社区（B站） |
| --- | --- | --- |
| 物料 | 生命周期长（版本/角色/攻略），SSR 级内容稀缺 | 洪水YNAnimator流量，时效性强，UGC 量大 |
| 目标 | 留存、社区氛围、ugc 生产激励 | 时长、互动、UP 主生态健康 |
| 冷启动 | 新版本/新角色上线峰值尖 | 新人 UP 主需要保量扶持 |
| 特殊 |跨端（游戏内/社区 App）行为打通 | 直播的实时性 + 房间进出 dynamics |

**答这类的关键**：先说出两者的差异，再说"所以 metric 和冷启动策略要分别设计"，
而不是给出一个万能方案。

## 3. 推荐算法八股（速记版）

> 只列面试真可能问到的，以及容易被追问到的项目相关题。

**召回 / 向量检索**
1. 双塔为什么适合召回？→ 用户/物品向量可离线计算，ANN 毫秒检索，代价是交互发生在最后一层（表达力弱）。
2. Faiss IVF 的 nlist / nprobe 怎么调？→ nlist 越大簇越细，nprobe 越大召回越高但越慢；一般先 `sqrt(N)` 起 nlist。
3. HNSW 和 IVF 的区别？→ HNSW 图索引，高召回低延迟但内存大、构建慢；IVF 更适合超大库 + 可增量。
4. ItemCF 的相似度为什么要除以 √(count_i × count_j)？→ 归一化避免热门 item 与所有 item 都相似（余弦 vs 原始共现）。
5. Swing / IUF / 时间衰减各自解决什么？→ 抑制 false-positive 共现 / 抑制活跃用户 / 抑制过期信号。

**排序**
6. Wide&Deep / DeepFM / DCN / xDeepFM 的演进？→ 记忆vs泛化；FM 替代手工交叉；Cross Net 显式高阶；CIN 向量级交叉。
7. attention 在 DIN 里为什么要 mask padding？→ 否则 padding 位置会分走权重，序列长度变成噪声。
8. 序列建模 DIN → DIEN → SIM/ETA 的区别？→ 静态 attention → 兴趣演化 → 长序列检索式建模（两段式）。
9. pos/neg sampling 对 loss 的校准影响 → 见 C2。

**多目标**
10. ESMM 的损失函数 → `CE(pCTR,y_click) + CE(pCTCVR, y_click*y_cvr)`。
11. MMOE/PLE 解决什么 → 任务间负迁移，多 expert + gate / 显式分离共享与独有 expert。
12. 多目标怎么融合成最终排序 → 加权乘法(`ctr^α × 时长^β`) / 帕累托最优 / 强化学习调权。

**生态与增长**
13. 评价指标为什么用 GAUC 而不是 AUC → AUC 混淆了用户间的比较，线上是按用户分发的。
14. ILD / Coverage / Novelty 分别描述什么 → 列表内多样性 / 库覆盖 / 是否偏好冷门。
15. Lift@k 的定义 → Top-k 命中率 / 全量命中率。

## 4. 我的失败经验（主动说这些很加分）

1. **DIN 目标泄漏**：train loss 0.44→0.24 很漂亮，valid AUC 却 0.65→0.60。修复方式见 STAR-2。
   → 教训：**先看 valid/test，再看 train loss**。
2. **画像特征穿越**：第一版用全量数据算热度。→ 教训：**切分先于特征**。
3. **增长标签退化**：留一法切分下"用户未来价值"退化成 0/1，所有 Lift 都是 1.0x。
   → 教训：**指标的分辨率决定了它能不能用**，增长类任务必须单独按时间窗口切。
4. **ItemCF 比双塔还强**：在小物空间里这是事实，我没有掩盖。（0.188 vs 0.207，
   差异只有 1.8pt，说明 Embedding 侧还有调参空间。）
   → 教训：** simple baseline 一定要先跑，不然你不知道复杂模型到底有没有价值。**
