## 1. 场景建模：把 MovieLens 映射成内容社区漏斗

MovieLens 的显式评分（1–5）本身不是推荐系统的目标，需要先定义业务漏斗：

| 漏斗层级 | 定义 | 数据构造 |
| --- | --- | --- |
| 曝光 | 候选物料库 | 全部 3883 个 item |
| 点击 | rating ≥ 4 | 作为正样本（隐式反馈的标准做法） |
| 转化 | rating = 5 | 深度互动：完播/点赞/收藏的代理指标 |
| 负样本 | 用户未交互过的 item | popularity^0.75 采样，比例 1:4 |

这样一条数据结构就能同时支撑召回（点击二分类）与多目标（CTR + CVR）建模。

**为什么负采样要 popularity^0.75 而不是均匀？**
均匀负采样会让模型过度关注长尾：大量从未被任何人点过的 item 被当作"用户不感兴趣"，
但这些样本多数从未真正曝光过（曝光偏差）。用 0.75 次幂加权后负样本分布更接近真实曝光分布，
同时又不至于完全被头部垄断（0.75 而不是 1.0 就是为了保留中长尾信号）。

## 2. 训练 / 验证 / 测试切分

**留一法（leave-one-out）**：每个用户按时间排序后，最后一次点击 → test，倒数第二次 → valid，其余 → train。

- 比随机切分更贴近真实：预测的是"下一个"，而不是"随机某个"；
- 每个用户只有 1 个测试正例，评测时对 3883 个候选做全库排序，指标口径统一（Recall/NDCG/HitRate）；
- 代价：无法评估"多个未来行为"的价值，所以**增长模块另起了一套时间窗口切分**（见 §6）。

三种 split_tag：`train` / `valid` / `test` / `cold` / `unclick`（低分交互，不参与训练但参与画像消融外的统计）。

## 3. 特征工程

### 3.1 DuckDB SQL 画像（`src/recsys/data/sql/`）

用户侧：行为规模、点击率、转化率、 Rating 均值与标准差、活跃月数、生命周期、近 10 次均值（口味漂移）。
物品侧：热度、口碑、时间衰减热度（半衰期 30 天）、去重用户数、年龄。

时间衰减热度的意义在于解决**老内容的马太效应**：一部 2000 年的老片累积的点击数天然高于新内容，
用 `exp(-ln2·Δt/30d)` 加权后，热度排序更接近"当下"，热榜才不会变成"二十年不变的榜单"。

### 3.2 为什么画像只用 train 统计

这是最容易出错、也最容易被忽略的泄漏：**用全量数据（含 test）算物品热度，等于告诉模型测试物品很热门**。
离线指标会明显虚高，落地后必然回落。本仓库在 `01_prepare_data.py` 里先切分再算特征，
物品的 popularity 全部来自训练集窗口。

### 3.3 稠密特征归一化

`log1p → z-score`。所有 count 类特征长尾极重，直接喂 MLP 会被极端值主导。
冷启动物品 count=0 → log1p 后为 0 → 标准化后是负均值偏移，这个负值本身就是"没有历史"的信号，保留它是有用的。

## 4. 召回层

### 4.1 三路各自的职责

| 通道 | 解决什么问题 | 弱点 |
| --- | --- | --- |
| ItemCF（IUF + Top100 近邻） | 强共现信号，对老用户极稳 | 冷启动无解，相似度矩阵 O(N²) |
| 双塔向量 | 可泛化、能接内容特征、支持 ANN 毫秒检索 | 信息压缩到 64 维，小数据集打不过 CF |
| 时间衰减热榜 | 全新用户 / 兜底 / 保底多样性 | 完全无个性化 |

**IUF（Inverse User Frequency）**：给活跃用户的行为降权。一个看了一万部片子的用户，
他看什么都会制造"共现"，这种信号应该稀释；只看十部的人的一次共现反而更有信息量。

### 4.2 为什么用 RRF 而不是分数加权融合

三路的分数不在同一个量纲（余弦相似度 vs 相似度加权和 vs 衰减权重），
分数直接相加需要归一化，而归一化的尺度又会随数据分布漂移变化。
RRF（`score = Σ w_i / (60 + rank_i)`）只依赖 rank，天然免疫量纲与分布漂移，
代价是丢掉了分数本身的"置信度"信息——在召回阶段这个交换是划算的。

### 4.3 ANN 选型

见 README §4.2。核心结论：**索引选择由库规模决定**。
- 万级以内：Flat（SaveStorage 简单，latency 可接受）；
- 十万到百万：IVF-PQ，nprobe 作为召回率/延迟的连续旋钮；
- 高维且要求高召回：HNSW（本仓库实测 20 万规模下 HNSW 延迟略优于 IVF，但召回掉了 2.8pt）。

## 5. 排序层

### 5.1 DeepFM

FM 二阶显式交叉 + DNN 隐式交叉共享同一份 embedding。
选择它的原因是**它是"没有序列、只有 id 类和画像特征"时的合理上限**，适合作为 DIN 的对照基线（ ablation 只看结构变量）。

### 5.2 DIN：target attention

候选 item 作为 query，对历史序列做加权池化。
相比简单平均池化（YouTube DNN 的做法），DIN 的关键改进是**让相似度依赖候选**：
推动作片时激活历史里的动作片，推文艺片时激活文艺片，而不是永远用同一个用户向量。

### 5.3 ESMM：为什么不能直接训 CVR

转化样本只在"已点击"的子集里有标签。如果只用点击后的样本训 CVR 模型，
训练空间（点击样本）和推理空间（全部曝光）不一致，这就是 **SSB（Sample Selection Bias）**。
ESMM 的解法：

```
pCTCVR = pCTR × pCVR
loss   = CE(pCTR, y_click) + CE(pCTCVR, y_click × y_convert)
```

全程在曝光空间上监督，CVR 塔被"捎带"训练出来，不需要从未点击样本里编造负标签。
本仓库实现的就是这个版本（共享底层 + 双塔），并保留 `use_sequence` 开关做结构消融。

### 5.4 两个泄漏事故复盘

**（a）DIN 目标泄漏**
最初训练时，用户的行为序列包含了当次目标 item 本身，模型学到一条极简捷径：
"这个 item 出现在历史里 → 预测点击"。结果 train loss 从 0.44 一路降到 0.24，
但 valid AUC 从 0.65 **跌到 0.60**（对while 这个 (trajectory) 反而 0.60 是因为
评测时正例的目标不在历史里 → 全部被预测为低分）。

修复方式是**按曝光时刻做因果截断**：为每条样本计算 `hist_keep`（该时刻之前还有几条行为），
在 `build_batch` 里把之后的位置 mask 成 -1。负样本与对应的正样本共享同一个 keep 值，
否则模型会从"历史长度"反推出标签——这是同一个坑的第二层。

修复效果：双塔 valid Recall@50 0.145 → 0.215；DIN AUC 0.60 → 0.819。

**（b）画像特征穿越**
见 §3.2。

这两条都已经写成测试：`tests/test_data.py` 里的 `test_causal_mask_file_consistency`、
`test_processed_dataset_has_no_train_test_leak`、`test_cold_items_excluded_from_training`。

## 6. 增长层：为什么增长任务必须重新切分

留一法下每个用户的"未来"只有 1 条行为，用它定义用户价值会得到 0/1 标签且几乎人人命中
（第一版跑出来所有 Lift 都是 1.0x，毫无意义）。

所以增长模块单独用**时间窗口切分**：时间戳 80% 分位点之后的所有行为作为未来窗口
（112,448 条），之前的行为只用于算特征。

另一个容易忽略的点：**不能用全量训练集学出来的双塔用户向量来做 Lookalike**，
因为那些向量里包含了未来窗口的行为。本仓库的做法是只用 past window 的行为矩阵
现算 TruncatedSVD 用户向量（解释方差 38%），保证"推过去"看不"。

pLTV 用 HistGradientBoostingRegressor 而非复杂模型：增长场景里
"能不能向业务解释谁是高价值用户"和 AUC 同等重要，permutation importance
给出的 Top 特征是 `active_months`、`convert_rate`、`past_mean_rating`——这些都是可运营的解释。

## 7. 冷启动层

设计成"独立通道 + 额度"而不是"让主模型推荐新内容"，因为后者在数学上不成立：
从未训练过的 ID Embedding 是随机初始化，它在向量空间里的位置没有任何语义。

给内容侧留的入口有两条：
1. **语义通道**：bge-small-en-v1.5 把标题 + 类目编码为 384 维向量，用户画像 = 历史内容向量均值；
2. **标签通道**：同一向量空间里与候选标签词表算余弦，取 Top3 作为结构化标签，再建倒排。

标签生成为什么用"受控词表 + 相似度打分"而不是让 LLM 自由生成？
因为推荐系统的标签必须**可控、可入库、可复现**。开放生成会产出长尾、不稳定、
且无法进倒排索引的词汇。真实系统里可以让 LLM 负责词表维护和长文本理解，
但落地球二醇还是这个受控词表。（本仓库保留了在线 LLM 润色的接口位。）

额度（quota）这个旋钮本身就是业务决策：**新内容该占多少流量**，
额度 20 的实验结果是 Recall@50 从 0 涨到 0.40、覆盖率 98.9%。

## 8. 重排层

精排是 pointwise 的，只看"这条内容值不值得点"，不看"这一屏有没有重复"。
结果就是 Top10 很可能是一整个系列的续作、同一个 UP 主的同类视频。

- **MMR**：`argmax[λ·rel - (1-λ)·max_sim(selected)]`，λ 是精度与多样性的连续旋钮；
- **类目打散**：硬约束同一级类目 ≤2 条。

实验发现类目打散**同时提升了 NDCG（+9%）和 ILD（+35%）**：
因为同质占位被移除后，真正相关的长尾内容终于有机会进入列表。
这条结论在不少业务场景都成立——打散不一定是"牺牲精度换多样性"。

## 9. 评测体系

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 召回 | Recall@K / HitRate@K | 库是 K 潜行 K 所以两者数值相同 |
| 排序 | AUC / GAUC / LogLoss | GAUC 先看用户内排序，避免被活跃用户主导 |
| 列表 | NDCG@K / MAP@K | 位置敏感，反映真实曝光收益 |
| 生态 | Coverage / ILD / Novelty | 覆盖率、列表内多样性、新颖度 |
| 增长 | Lift@K / Spearman / RMSE | 人群包质量、价值预估排序能力 |

GAUC 是本仓库最看重的排序指标：AUC 会把"冷门用户 1 条正例"和"热门用户 100 条正例"
同等看待，而线上流量恰恰是按用户分发的，广告/社区场景的真实体验由 GAUC 决定。
